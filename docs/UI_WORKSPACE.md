# AMENDMENT 2 TO THE WORKSPACE-UI TASK — DESIGN THE UI PROPERLY: AESTHETIC, CUSTOMISABLE, MODULAR, UX-FRIENDLY

Save this verbatim next to the workspace-UI prompt as docs/UI_WORKSPACE.md (both together form one task). Where they conflict, this amendment wins. All earlier rules apply (privacy, single-user, license gate, `npm audit` zero, no mock data, verification with real output). Owner-directed scope: record an ADR and a REVIEW_QUEUE entry.

## D0. DESIGN BEFORE CODE (do first; commit each artifact)
1. docs/design/BRIEF.md: two personas (a non-technical single owner who wants private answers from their own documents and voice; a power user who tunes models, tools and layouts), top tasks, design principles (calm, clear, fast, honest about privacy, forgiving, keyboard-first), and explicit non-goals.
2. docs/design/TOKENS.md and a token schema (JSON): color (semantic: surface, surface-raised, border, text-primary/secondary/tertiary, accent, success, warning, danger), type scale, spacing (8px grid), radii, shadows, motion durations/easings, z-index, density multipliers. Audit the existing Hermes-derived tokens and reuse them; add only what is missing.
3. docs/design/COMPONENTS.md: inventory in layers: tokens -> primitives -> composites (MessageList, Message, Composer, SessionList, SearchBox, ModelPicker, CitationChip, ToolCard, StatusItem, ...) -> panels -> layouts -> shell, each with states (default, hover, focus, disabled, loading, empty, error) and a11y notes.
4. docs/design/FLOWS.md plus low-fidelity wireframes as static SVG/HTML in docs/design/wireframes/ for: first run/onboarding; ask a question with documents (citations); voice conversation with barge-in; model switching; attach and ingest a folder; settings and customisation; destructive action with undo; error and engine-down states; mobile layouts. Wireframes are reviewed and revised before components are built.
5. docs/design/MICROCOPY.md: tone (plain, warm, specific), error format (what happened, why, what you can do), empty-state copy, privacy wording that is truthful (never "100% secure"; state exactly what is verified). All user-facing strings live in a single string table (i18n-ready, no hardcoded strings in components).

## D1. MODULAR ARCHITECTURE (first-party only; no third-party plugin or code loading)
- A typed PanelRegistry: each panel declares id, title, icon, allowed slots (left, center, right, bottom), required backend capabilities, default visibility, lazy loader, min/max size, and keyboard shortcut. The shell renders only panels whose capabilities are present (discover via a capability endpoint built from real config/health; add one if missing, authenticated, with tests). Adding a panel must require only a registry entry plus its component; prove it with a test that registers a dummy panel.
- Each panel is wrapped in an error boundary (one panel crashing never takes down the app), code-split, and has a performance budget.
- Separate data from presentation: typed API client plus hooks/store layer; presentational components receive props and are testable in isolation. State management choice by ADR (prefer what the repo has; a new library needs the license, audit and bundle checks).
- A small in-repo design gallery route (dev/test build only, excluded from release bundles) rendering every primitive and composite in all states, themes and densities; used for screenshots and regression. Do not add Storybook-class dependency trees unless an ADR justifies it and the audit stays at zero.

## D2. CUSTOMISATION (data-only; no user-supplied code or CSS)
- Theme: light/dark/system, the existing theme set, an accent color picker with an enforced WCAG AA contrast check (reject or auto-adjust failing combinations), custom themes defined as JSON tokens validated against the token schema (reject unknown keys, remote URLs, `url()`, `@import`, and any non-token content). Import/export a theme or the full UI preferences as a local JSON file; reset to defaults at any scope.
- Density (compact/comfortable/spacious), interface font size scale (e.g. 90–125%), font choice among the already bundled license-verified fonts, message layout (document-style versus bubbles), content width, code-block theme, animation level (full/reduced), timestamp and avatar visibility, Enter versus Shift+Enter send behavior.
- Layout: the four presets from the workspace prompt plus user-defined saved layouts (named, reorderable, stored as data: which panels in which slots with sizes); drag to rearrange panels between allowed slots with keyboard-accessible alternatives; sidebar side switch.
- Keyboard shortcuts: documented in-app, rebindable with conflict detection and per-shortcut reset.
- Persistence: UI preferences only (never credentials, drafts or conversation content in browser storage). Preferred: authenticated server-side preferences in the gateway's SQLite (so they follow the owner across devices in LAN mode), validated by schema with a migration and tests; a localStorage fallback only if the ADR justifies it. Live preview before applying; corrupted or invalid preferences fall back safely to defaults with a notice, never a broken UI.

## D3. UX FRIENDLINESS (concrete requirements)
- First-run onboarding: short, skippable, and truthful: shows the detected hardware tier and chosen profile, model download with progress, cancel and fit estimates, a "private by design" explanation backed by the live egress self-test result, picking a folder for Knowledge, then a first prompt suggestion. Returning users never see it again unless they ask.
- Progressive disclosure: simple surface by default; advanced controls behind clearly labeled sections. Empty states teach (what to do next). Every icon-only control has a tooltip with its shortcut. Command palette (Ctrl/Cmd+K) searches real actions, sessions and settings.
- Forgiving: undo toasts for delete/purge-adjacent actions (soft delete window), confirmation only where destructive and irreversible (Full Purge uses typed confirmation), drafts preserved in memory across tab switches, no data loss on accidental navigation.
- Feedback: skeletons for loading, determinate progress with cancel for model downloads and ingestion, streaming that never janks (virtualize long transcripts, stick-to-bottom with a "Jump to latest" control, preserve scroll when the user scrolls up), clear states for engine busy (queued position or Retry-After), engine down, and offline.
- Chat details: message actions that really work (copy, retry, stop, delete; edit/regenerate/branch only if the backend supports them), code block copy, citation chips opening the exact source passage, Markdown export of a conversation to a local file, paste and drag-drop attachments with validation.
- Accessibility: WCAG 2.2 AA target; full keyboard operation; logical focus order and focus return after dialogs; ARIA live regions for streaming status (not for every token); screen-reader labels; contrast; touch targets >= 44px on mobile; reduced motion; zoom to 200% without loss of function.
- Performance budgets set by ADR before measuring: first load, interaction latency (INP) on typing and panel toggles, bundle size per route/panel, no layout shift on streaming.

## D4. WORKFLOW AND ORDER (replaces section 6 of the workspace prompt)
D0 design artifacts and wireframes -> token schema and primitives audit -> D1 registry, layout engine and shell (with the capability endpoint) -> sidebar, tabs, composer and message list -> right rail, status bar -> settings overlay with the D2 customisation system -> onboarding and command palette -> polish pass. After each step: build the real feature, capture screenshots (light/dark, at least three themes, compact/comfortable densities, 1440x900, 820x1180, 390x844), open and critique the screenshots yourself against docs/design/CRITIQUE.md (alignment, spacing rhythm, hierarchy, contrast, truncation, empty/error states), fix, and re-capture. Keep at least two critique iterations per major screen on record. Every slice: contract/tests first, regression, coverage and ui-deviations rows updated, commit, push, poll hosted CI to `completed`.

## D5. VERIFICATION (numbers; no claims without evidence)
- Playwright task scenarios with budgets recorded as measured numbers (clicks and time): first answer from a fresh install in <= N clicks after onboarding, change theme/accent/density, save and restore a layout, rebind a shortcut, ingest a folder and get a cited answer, rearrange panels with keyboard only, recover from engine-down, undo a delete. Set N and thresholds by ADR before measuring.
- Heuristic evaluation (Nielsen's ten) per major screen recorded in docs/design/UX_ACCEPTANCE.md with findings and fixes. User research with real people is NOT possible here: mark it UNVERIFIED and provide a short five-participant test script for the owner.
- Customisation tests: invalid/hostile theme JSON rejected; contrast guard enforced; import/export round-trips; preferences migration and corrupted-data fallback; layouts restore exactly; registry hides panels lacking capabilities; error boundary isolates a crashing panel; string table has no hardcoded strings (lint check).
- Plus everything in the workspace prompt's section 7 (axe, keyboard-only, egress test with every foreign origin aborted, bundle budget, XSS suite, Hermes fidelity numbers where the harness exists, `npm audit` zero, hosted CI green on the exact head).
